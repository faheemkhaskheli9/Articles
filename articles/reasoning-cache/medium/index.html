Stop Making Your LLM Solve the Same Problem Twice

Build a validated reasoning cache in Python, understand when it saves money, and learn why safe reuse is harder than storing answers.

Most AI agents treat each new request as another problem for a large language model. But a business agent might calculate a discount today, then calculate the same kind of discount tomorrow with different numbers. A response cache cannot reuse the old answer; it might be able to reuse the procedure that produced it.

Recent research into this idea includes CPU-ARC: Agentic Reasoning Caching for on-CPU Reasoning Reuse, published in November 2026. The authors report 16–291 times lower cost per cached invocation on the tasks they evaluated. That does not include the full cost of constructing each cache entry or prove similar savings in an enterprise application.

This article teaches an independently developed engineering demonstration, not the paper's full implementation. The companion repository contains the complete Python project, including tests, dependencies, an optional model-assisted builder, and VS Code debugging configurations.

1. A realistic starting point: checkout support

Imagine a customer-support agent processing this request:

Calculate checkout total: subtotal $120, discount 10%, tax 8%, shipping $5.

Our example has four precise rules. Apply the discount first. Calculate tax on the discounted subtotal. Do not tax shipping. Round monetary steps to two decimals using the ROUND_HALF_UP policy.

The discount is $12. The taxable subtotal is $108. The tax is $8.64. Add $5 shipping, and the final total is $121.64.

Now a second customer asks:

Compute total: shipping $0, tax 8%, discount 15%, subtotal $200.

The correct result is $183.60. The values and word order changed, but the rules did not.

Expert caveat: If you already know these rules, the correct first move is to write an ordinary Python function. An LLM is not needed for straightforward arithmetic. Reasoning caches become more interesting when an agent encounters many recurring task families that were not anticipated when the software was written.

2. Cache the procedure, not the previous answer

Our cache entry does not store “$121.64” as a reusable response. It represents four parameterized operations:

  1. Discount amount: subtotal multiplied by discount percentage, divided by 100.
  2. Taxable subtotal: subtotal minus discount amount.
  3. Tax amount: taxable subtotal multiplied by tax percentage, divided by 100.
  4. Total: taxable subtotal plus tax amount plus shipping.

These steps are stored as a restricted arithmetic program. The evaluator interprets only approved mathematical syntax and named variables, using Python Decimal arithmetic. It does not execute arbitrary generated Python with eval or exec.

You can inspect the actual implementation in the complete Python example. This distinction matters: source code stays in GitHub, where it remains readable, testable, and copyable. 3. Route requests conservatively

Before executing a stored procedure, the agent must decide whether the procedure applies. Similarity is not enough.

“Apply 10% discount, then tax the discounted amount” and “include shipping in the taxable base” can sound almost identical, yet require different calculations. A semantic retriever may identify candidates, but a second check must enforce the actual business contract.

Our demo extracts the subtotal, discount percentage, tax percentage, and shipping charge from deliberately structured requests. It rejects missing values, duplicates, unsupported policy changes, and invalid ranges. For a task outside the contract, it returns a verified fallback instead of forcing a false cache hit.

What experienced engineers optimize: false cache hits matter more than false cache misses. A miss costs another model call. A wrong hit can silently produce a bad invoice.

4. Run the full implementation

The project supports Python 3.11 or newer and works offline for the curated cache demonstration.

  1. Clone the Articles repository using the command git clone https://github.com/faheemkhaskheli9/Articles.git.
  2. Open the examples/reasoning-cache folder.
  3. Create a Python virtual environment using python -m venv .venv, then activate it with the command appropriate to your operating system.
  4. Install dependencies using python -m pip install -r requirements.txt and python -m pip install -e ..
  5. Seed the validated procedure using python -m reasoning_cache --seed.
  6. Run the tests using python -m pytest -q.

To try another input, run the CLI with the --request option followed by the customer message. The response contains a route, procedure identifier, and calculated values.

For the second customer, the expected total is 183.60. If the cache is absent or the policy is unsupported, the demo uses an independent reference calculation rather than pretending there was a cache hit.

The example README includes exact commands for Windows, macOS, and Linux, plus VS Code launch settings. You do not need an API key for the offline scenario.

5. Let a model propose a procedure—and verify it

Constructing a procedure from a previous solution is the more interesting part of reasoning caching. Our optional builder asks a source model to solve an example, then asks a builder model to propose a constrained JSON arithmetic program. The proposed program is checked before it is allowed into the registry.

To try this, copy .env.example to .env, set your OPENAI_API_KEY, and run python -m reasoning_cache --build. This makes paid API calls and can reject an incorrect generated proposal.

A model-generated function is a candidate, not a trusted capability. The demo validates allowed operations, numeric boundaries, and reference examples. Its arithmetic-only language is deliberately narrow; it does not make arbitrary generated code safe to execute.

There is also a deeper limitation. Our checkout project already has an independently written reference implementation. A general agent encountering a novel task may not have an oracle. Finding credible tests for newly discovered capabilities is among the hardest open engineering problems in procedural memory.

6. Test the failure cases that matter

Test the happy path, but spend at least as much effort on when the cache should refuse a request. Useful test families include:

  • Contract mismatches: shipping becomes taxable or rounding rules change.
  • Invalid inputs: discount exceeds 100%, values are missing, or fields contradict each other.
  • Unsafe proposals: generated expressions try to access attributes, call functions, import modules, or consume excessive resources.
  • Cache corruption: the registry contains malformed or outdated entries.
  • Independent correctness: randomized inputs and mathematical invariants are compared with trusted calculations.

Passing a small test suite is useful but not sufficient for production. High-impact procedures require more extensive fuzzing, isolation, versioning, human approval, and observability. In particular, comparing a generated procedure only with the original model's answer can preserve the model's original mistake.

7. Decide whether caching is worth the complexity

Procedure construction consumes tokens and time. Routing consumes resources on every request. Some requests miss the cache. A reusable procedure pays for itself only when repeated, validated execution saves more than those overheads.

A simple break-even estimate is: required request count is greater than build cost divided by the net expected saving per request. The expected saving depends on valid-hit rate, original-model cost, cached-execution cost, and routing overhead.

Do not report only the cache-hit rate. Measure verified hit rate, incorrect-match rate, end-to-end latency, amortized builder cost, invalidations, fallback frequency, and data drift.

For predictable workflows, conventional code is usually simpler. For highly novel tasks, safe procedure reuse may be impossible. Between these extremes is the opportunity: repeated problem families that agents can translate into validated, reusable software.

The aim is not to eliminate reasoning. It is to stop paying for reasoning when a verified procedure already solves the task.
